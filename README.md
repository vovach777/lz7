# lz7

LZ77-компрессор на C++17 с заголовочным энкодером (`include/lz7.hpp`) и декодером.

## Сборка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Таргеты:

- `lz7` — компрессор/декомпрессор.
- `lz7parser` — разбор входа, отладочный вывод токенов.
- `lz7dec` — отладочный дамп токенов декодера в stderr (не распаковка).

Интринсиков нет, бинарь по умолчанию переносимый. `-DLZ7_NATIVE=ON` добавляет `-march=native`; по замерам скорость от этого не меняется.

## Использование

```bash
./lz7 input.txt              # сжать -> input.txt.lz7
./lz7 input.txt out.lz7      # сжать в указанный файл
./lz7 -d input.lz7 out.txt   # распаковать
./lz7 -b input.txt           # только бенчмарк, файл не пишется
./lz7 -l4 input.txt          # уровень сжатия 1..4 (по умолчанию 2), также --level=N
```

## Архитектура

- Поиск матчей: хэш-таблица на 4-байтовых префиксах (`ENCODE_MIN = 4`) + цепочки позиций в общем кольце на `CHAIN_SIZE` элементов. Обход цепочки кончается на её конце, на выходе за окно, на протухшей ссылке (кандидат с чужим хэшем), после серии кандидатов подряд без улучшения (задаётся уровнем) или на потолке `MAX_ATTEMPTS` (256). Кандидат, не совпавший в байте, где кончается текущий лучший матч, отсеивается без полного сравнения. `HASH_LOG2` не больше 16: хэши `uint16_t`.
- Длина совпадения считается по 8 байт: `xor` двух `uint64_t`, первая разница через `ctz` (назад — `clz`). Это так же быстро, как прежние SSE-пути, и одинаково на всех архитектурах; нужен little-endian (на big-endian `#error`).
- Невыровненные чтения 32 бит идут через `memcpy` (`load_u32`), записи 32 бит в распаковщике (`src/main.cpp`) тоже через `memcpy`; без `reinterpret_cast`. Под `-fsanitize=undefined,address` roundtrip `samples/sqlite3.c` чистый.

## Уровни сжатия

Уровень задаёт, сколько соседних позиций проверяется за шаг (выбирается лучший матч из них) и после скольких кандидатов подряд без улучшения бросается обход цепочки. Размер и скорость — относительно прежнего режима 4×8, медианы замеров на Calgary, sqlite3.c, libstdc++ и enwik8:

| уровень | позиций × промахов | размер | скорость сжатия |
|---|---|---|---|
| `-l1` | 3×4 | +1.3…1.9% | ×1.30–1.79 |
| `-l2` (по умолчанию) | 3×8 | +0.14…0.53% | ×1.14–1.31 |
| `-l3` | 3×16 | −0.02…−1.0% | ×0.83–0.92 |
| `-l4` | 4×16 | −0.4…−0.9% | ×0.68–0.87 |

Три позиции выгоднее четырёх на любом бюджете промахов, кроме максимального: например, 3×6 и сжимает лучше, и работает быстрее, чем 4×4. Формат и декодер от уровня не зависят.

## Формат потока

Заголовка, размера и контрольной суммы нет: поток — последовательность токенов до конца входа. Многобайтовые поля little-endian. `ENCODE_MIN = 4`, `MAX_OFFSET = 131071`.

### Токены

Короткий матч, бит 7 = 1. Энкодер выбирает его при `offset < 1024 && literals < 4`:

```
1 xx LL MMM | lit[LL] | ofs_lo | [ext MMM]
offset    = xx<<8 | ofs_lo        1..1023
literals  = LL                    0..3, без расширения
match_len = MMM + 4 (+ext)
```

Длинный матч, бит 7 = 0:

```
0 x LLL MMM | [ext LLL] | lit[n] | ofs_lo ofs_hi | [ext MMM]
offset    = x<<16 | ofs_hi<<8 | ofs_lo   1..131071
literals  = LLL (+ext)
match_len = MMM + 4 (+ext)
```

Только литералы: короткий токен с нулевым смещением и `LL = 0`. Энкодер выдаёт его для хвоста литералов:

```
1 00 00 NNN | 00 | [ext NNN] | lit[n]
literals  = NNN (+ext)            без +4
```

### Расширение длины

Если 3-битное поле равно 7, за ним идут байты расширения, как в LZ4:
`v = 7; do { c = byte; v += c; } while (c == 255);`.
Расширение литералов стоит перед литералами, расширение длины матча — после смещения.

### Семантика

- `offset` не больше уже распакованного объёма, иначе ошибка формата.
- `offset < match_len` разрешён: копирование идёт побайтово, так кодируются серии.
- Конец потока — конец входа (или четыре нулевых байта на границе токена). Токен, обрезанный посередине, — ошибка; обрезку ровно по границе токена без размера в заголовке не отличить от конца.

### Цена заголовка

| | offset ≤ 1023 | offset ≤ 131071 |
|---|---|---|
| литералов 0–3 | 2 байта | 3 |
| литералов 4–6 | 3 | 3 |
| литералов 7–261 | 4 | 4 |

`match_len > 10` добавляет 1 байт расширения на каждые 255.

### Незадействованные комбинации

- Короткий токен с `offset = 0` и `LL = 1..3`: повтор паттерна из `LL` байт `MMM` (+ext) раз. Энкодер такой токен не выдаёт; `lz7::decode` его поддерживает. Планируется под управляющий токен.
- Длинный токен с `offset = 0`: ошибка формата (четыре нулевых байта на границе токена — конец потока).

## Декодер

`lz7::decode` (`include/lz7.hpp`) пишет прямо в буфер и берёт токен, только если ему хватает места вместе с `DECODE_SLACK` (32 байта): литералы и матчи со смещением от 8 копируются кусками по 16/8 байт без точной длины. Основную часть потока разбирает быстрый цикл по образцу `LZ4_decompress_generic`: пока до конца входа больше 32 байт, а до конца выхода больше 64, токен разбирается прямо по указателю, причём поля короткого и длинного токена считаются без ветвления и выбираются маской — тип токена непредсказуем, и эта ветка стоила до трети времени распаковки. Литералы копируются 16-байтным куском, матч до 10 байт при смещении от 8 — двумя по 8, длинные — кусками по 32. Нулевое смещение, ошибки и близость конца уходят в общий путь. Если места нет, он возвращает `NeedOutput` с нужным размером на начале токена, и `lz7 -d` перемапливает выходной файл (окно растёт геометрически, `MAX_OFFSET` байт истории сохраняются). Битый вход (обрезанный токен, смещение за начало окна, нулевое смещение в длинном токене) даёт ошибку, а не падение. `lz7::expand` с колбэками остался для отладочных `lz7dec`/`lz7parser`.

## Статус

- x86-64: сборка и roundtrip проверены.
- aarch64: компилируется clang'ом; код тот же, что на x86, архитектурных веток нет. На железе не запускался.

## Тесты

`tests/` содержит скрипты для Windows и macOS: они прогоняют `samples/` через `lz7parser` и `lz7`/`lz7dec` и сравнивают логи токенов компрессора и декодера (`fc` / `diff`). Сравниваются дампы токенов, а не байты распакованного файла.
