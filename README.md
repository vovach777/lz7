# lz7

LZ77-компрессор на C++17 с заголовочным энкодером (`include/lz7.hpp`) и декодером.

## Сборка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Таргеты:

- `lz7` — компрессор/декомпрессор.
- `lz7parser` — разбор входа, отладочный вывод токенов.
- `lz7dec` — отладочный дамп токенов декодера в stderr (не распаковка).

На x86 CMake добавляет `-mavx -msse4.2 -mssse3 -march=native`. На других архитектурах эти флаги не ставятся.

## Использование

```bash
./lz7 input.txt              # сжать -> input.txt.lz7
./lz7 input.txt out.lz7      # сжать в указанный файл
./lz7 -d input.lz7 out.txt   # распаковать
./lz7 -b input.txt           # только бенчмарк, файл не пишется
```

## Архитектура

- Поиск матчей: хэш-таблица на 4-байтовых префиксах (`ENCODE_MIN = 4`) + цепочки позиций в общем кольце на `CHAIN_SIZE` элементов. Обход цепочки кончается на её конце, на выходе за окно, на протухшей ссылке (кандидат с чужим хэшем), после `MISS_STREAK` (8) кандидатов подряд без улучшения или на потолке `MAX_ATTEMPTS` (256). Кандидат, не совпавший в байте, где кончается текущий лучший матч, отсеивается без полного сравнения. `HASH_LOG2` не больше 16: хэши `uint16_t`.
- Хэш для четырёх соседних позиций считается SIMD-инструкциями: SSE4.1 на x86, NEON на ARM, скалярный fallback в остальных случаях. Все три пути дают одинаковый результат.
- Невыровненные чтения 32 бит идут через `memcpy` (`load_u32`), записи 32 бит в распаковщике (`src/main.cpp`) тоже через `memcpy`; без `reinterpret_cast`. Под `-fsanitize=undefined,address` roundtrip `samples/sqlite3.c` чистый.

## Формат потока

Заголовка, размера и контрольной суммы нет: поток — последовательность токенов до конца входа. Многобайтовые поля little-endian. `ENCODE_MIN = 4`, `MAX_OFFSET = 131071`.

### Токены

Короткий матч, бит 7 = 1. Энкодер выбирает его при `offset < 1024 && literals < 4`:

```
1 xx LL MMM | lit[LL] | ofs_lo | [ext MMM]
offset    = xx<<8 | ofs_lo        1..1023
literals  = LL                    0..3, без расширения
match_len = MMM + 4 (+ext)
```

Длинный матч, бит 7 = 0:

```
0 x LLL MMM | [ext LLL] | lit[n] | ofs_lo ofs_hi | [ext MMM]
offset    = x<<16 | ofs_hi<<8 | ofs_lo   1..131071
literals  = LLL (+ext)
match_len = MMM + 4 (+ext)
```

Только литералы: короткий токен с нулевым смещением и `LL = 0`. Энкодер выдаёт его для хвоста литералов:

```
1 00 00 NNN | 00 | [ext NNN] | lit[n]
literals  = NNN (+ext)            без +4
```

### Расширение длины

Если 3-битное поле равно 7, за ним идут байты расширения, как в LZ4:
`v = 7; do { c = byte; v += c; } while (c == 255);`.
Расширение литералов стоит перед литералами, расширение длины матча — после смещения.

### Семантика

- `offset` не больше уже распакованного объёма, иначе ошибка формата.
- `offset < match_len` разрешён: копирование идёт побайтово, так кодируются серии.
- Конец потока — конец входа.

### Цена заголовка

| | offset ≤ 1023 | offset ≤ 131071 |
|---|---|---|
| литералов 0–3 | 2 байта | 3 |
| литералов 4–6 | 3 | 3 |
| литералов 7–261 | 4 | 4 |

`match_len > 10` добавляет 1 байт расширения на каждые 255.

### Незадействованные комбинации

- Короткий токен с `offset = 0` и `LL = 1..3`: декодер трактует его как повтор паттерна из `LL` байт `MMM` раз (`fill_pattern`). Энкодер такой токен не выдаёт, реализация в `src/main.cpp` неверна (`memmove` не размножает паттерн, `count = 0` роняет декодер). Планируется под управляющий токен.
- Длинный токен с `offset = 0`: энкодер не выдаёт; декодер принимает четыре нулевых байта на границе токена за конец потока.

## Статус

- x86-64: сборка и roundtrip проверены.
- ARM (NEON): пути хэша и сравнения блоков компилируются под aarch64, но на реальном железе ещё не запускались.

## Тесты

`tests/` содержит скрипты для Windows и macOS: они прогоняют `samples/` через `lz7parser` и `lz7`/`lz7dec` и сравнивают логи токенов компрессора и декодера (`fc` / `diff`). Сравниваются дампы токенов, а не байты распакованного файла.
